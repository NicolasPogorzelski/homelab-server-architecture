# LXC250 - DevOps Workstation

This document describes the central DevOps management node (LXC250).

All Git operations, code editing, and infrastructure-as-code work happen exclusively on this node.

## Purpose

- Central Git repository management (push/pull to GitHub)
- Code editing (Neovim, VS Code Remote SSH)
- Ansible control node (manages all 9 nodes via SSH over Tailscale)
- IaC development and testing
- SSH jump point for administrative access to other nodes

## Runtime Characteristics

- Unprivileged Debian 12 LXC
- CTID: 250
- Hostname: `devops`
- Resources: 2 cores, 2048 MB RAM, 512 MB swap
- Disk: 8 GB on local-lvm
- Nesting enabled (required for Tailscale)
- Onboot: yes

## LXC Configuration

Tailscale TUN configuration (CT210-pattern, see [DD#13](../decisions/design-decisions.md#13-standardized-tun-configuration-for-tailscale-capable-lxcs)):

    lxc.cgroup2.devices.allow: c 10:200 rwm
    lxc.mount.entry: /dev/net/tun dev/net/tun none bind,create=file

Note: `lxc.cgroup2.devices.allow` was missing during initial provisioning
and was added during `chore/tailscale-tun-cleanup`.

### SSH / Tailscale Startup Dependency

SSH on LXC250 binds exclusively to the Tailscale IP. On reboot, `ssh.service`
starts before Tailscale has brought up the interface - the bind fails and SSH
remains down until manually restarted.

Fix: systemd drop-in at `/etc/systemd/system/ssh.service.d/override.conf`:

    [Unit]
    After=tailscaled.service
    Wants=tailscaled.service

    [Service]
    Restart=on-failure
    RestartSec=15s
    RestartPreventExitStatus=

`RestartPreventExitStatus=` (empty) overrides the upstream value of `255`,
which would otherwise prevent systemd from restarting SSH on bind failure.

## Ansible Setup

This node is the Ansible control node for the entire platform.

- **Inventory:** 9 nodes across two groups (`lxcs`, `vms`); real IPs gitignored, `hosts.yml.example` in repo
- **Remote user:** dedicated `ansible` user on every managed node, SSH key from LXC250, NOPASSWD sudo via `/etc/sudoers.d/ansible`
- **Vault:** `~/.vault_pass` (chmod 600, gitignored) auto-loaded via `vault_password_file` in `ansible.cfg`
- **Playbooks:** `apt-upgrade`, `bootstrap-ansible-user`, `node-exporter`, `prometheus-config`, `paperless-env`
- **Roles:** `node_exporter`, `prometheus_config`, `paperless_env`

See: [Ansible Platform](../platform/ansible.md)

## User Model

- Service user: `devops` (UID 1000, member of sudo group)
- Root access: via sudo
- SSH key authentication configured for admin devices

## Repository Layout

Git repositories are stored under:

- `/home/devops/git/homelab-server-architecture`

This checkout tracks `main` only. Playbooks execute from the working tree, so a node parked on a
feature branch or left mid-merge runs code that corresponds to no commit. Update with

### Tailscale Serve

Not applicable. This node does not expose web services. Access is SSH-only.

## Security / Exposure

- SSH binds exclusively to the Tailscale IP (<tailscale-ip-lxc250>:22)
- Authentication: SSH key only (ED25519) from admin-tagged devices
- No public exposure / no router port forwarding
- Remote access provided exclusively via Tailscale (identity-based overlay)
- Network policy enforced via Tailscale ACL (node tags + ACL JSON)
- See: [docs/platform/tailscale-acl.md](../platform/tailscale-acl.md)
- LXC TUN config follows CT210-pattern (DD#13)

## Access Model (Zero Trust)

- Administrative node with broad access to all tiers
- No service provider role (does not expose ports to other nodes)
- Outbound-only access pattern: SSH to other nodes, Git push/pull to GitHub
- Network segmentation enforced via Tailscale ACL

## Storage

- No external storage mounts
- All data is local to the container (Git repos, config files, SSH keys)
- No CIFS/SMB dependencies

## Failure Impact

If LXC250 becomes unavailable:

- No infrastructure changes can be pushed (Git, Ansible)
- Running services are NOT affected (devops is not in the data path)

Recovery is not "recreate the LXC and re-clone from GitHub" - that is what this section said
until 2026-07-28, and it understated the loss. Three artefacts live only on this node, all
gitignored and none backed up anywhere:

| Artefact | Consequence if lost |
|---|---|
| `~/.vault_pass` | Unrecoverable. Every vaulted secret in the repo becomes undecryptable. There is no restore path. |
| `ansible/inventory/hosts.yml` | Real Tailscale IPs; must be reconstructed by hand |
| Ansible SSH key (`~/.ssh/id_ed25519`) | Trusted by the `ansible` user on all 9 nodes; recoverable only by re-running the bootstrap over the whole fleet via break-glass |

The container also sits on the boot SSD with the unresolved I/O faults of
[KE-14](../platform/known-errors.md#ke-14), so this is not a hypothetical.

This node is operationally non-critical for service availability, and a single point of failure
for recoverability of the automation. Those are not the same property.

## Open Items (2026-07-28)

This node is the only one outside the system it manages. It appears in no inventory group, so
`hosts: all` (`ssh-hardening`, `systemd-hygiene`, `node-exporter`, `fleet-health-check`) and
`hosts: lxcs` (`apt-upgrade`) all silently skip it, and `unattended-upgrades` targets `vm100` only.
Consequences and the agreed plan:

1. **Secrets escrow** - `~/.vault_pass` and a copy of `hosts.yml` into Vaultwarden (lxc240). The
   node only ever pulls, never pushes, so its GitHub key should be demoted to a **read-only deploy
   key** in the same pass. No repo change; do this first.
2. **Inventory adoption** (`feat/lxc250-ansible-adoption`) - add to `lxcs` with
   `prometheus_label: devops` (the Prometheus template loops `groups['lxcs']`; without the label it
   renders an empty target), re-run `prometheus-config.yml`. This grants `NodeDown`,
   `SystemdUnitFailed`, a disk alert on the 8 GB root, and Ansible-driven patching in one move.

   **Correction (measured 2026-08-13): this node is not missing a `node_exporter` - it is running
   a wrong one.** A hand-written `/etc/systemd/system/node_exporter.service` dated 2026-04-22
   starts `/usr/local/bin/node_exporter` with no arguments, so it binds `*:9100` and answers
   `HTTP 200` on `/metrics`. Two consequences, and the second is the one that matters:
   - It is LAN-exposed, violating the platform binding rule - the third instance of this exact
     defect, after `postgres_exporter` on lxc260 (fixed 2026-07-10) and the host's own exporter
     (fixed 2026-07-14). Both of those were found by sweeping; this one was missed because a node
     absent from the inventory is also absent from every sweep.
   - Nothing scrapes it. Prometheus has 19 targets and lxc250 is not among them, so the metrics are
     produced and discarded. This is worse than having no exporter: `systemctl is-active
     node_exporter` answers `active` on this node, which reads as coverage.

   So the adoption task is a replacement, not an addition: the role must take ownership of the
   unit (`--web.listen-address={{ ansible_host }}:9100`, `--collector.systemd`) rather than
   assume a clean node. Verify with `ss -tlnp | grep 9100` afterwards - `active` proves nothing
   about the bind. Run `ssh_hardening` with `--check --diff` first - it is being applied to the node the
   connection runs through; `pct exec 250 -- bash` from the Proxmox host is the fallback. Note that
   `validate-repo.sh` Check 13 hard-codes an exemption for this file ("excluded from inventory, has
   `## Ansible Setup` instead") - the exclusion is codified in the tooling, so lifting it means
   giving this doc a `## Configuration Management` section and dropping the exemption.
3. **The sshd drop-in is an unlisted KE-18 instance.** The hand-written
   `/etc/systemd/system/ssh.service.d/override.conf` documented above uses
   `After=tailscaled.service` plus `Restart=on-failure` / `RestartSec=15s` - a retry loop, not a
   readiness gate ([KE-18](../platform/known-errors.md#ke-18): ordering is not readiness). Adopt it
   into a role and convert it to `ExecStartPre=/usr/local/bin/wait-for-tailscale-ip.sh 90`, the
   pattern already used on lxc260 and the Proxmox host. Being hand-written, it is lost on a rebuild.
4. **Pre-flight gate** (`feat/control-node-preflight`) - `preflight.yml`, imported into each
   playbook via `import_playbook`, asserting a clean `main` in sync with `origin/main` and no
   conflict markers. This closes the failure found on 2026-07-28, where the tree was two commits
   behind and a `tailscale-cert.yml` run would have overwritten the live KE-18 fix with the
   pre-fix script - silently, since Ansible reports `changed` either way. Optionally add a drift
   metric via the textfile collector once item 2 gives the node an exporter.

Considered and rejected: an auto-pull timer (removes drift, but the node would adopt whatever is on
`main` without anyone noticing - trades awareness for convenience; reconsider only if manual pulls
become a nuisance, and then *alongside* the gate, not instead of it); ephemeral per-run clones
(binds a run to a commit and dissolves the problem class, but the vault password and inventory live
outside the repo by design and would need re-mounting each run - revisit for the Terraform track,
where state raises the stakes); Actions-triggered deploys on merge (needs a self-hosted runner in
the tailnet and fleet secrets in GitHub, and "on merge" is meaningless on a host that is powered
down overnight).
