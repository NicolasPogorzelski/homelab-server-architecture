# VM100 Services (GPU / Media)

## Purpose

- GPU-accelerated media streaming (Jellyfin with NVIDIA hardware transcoding)
- Audiobook hosting (Audiobookshelf)
- Local LLM inference backend (Ollama, backup node for AI stack)
- Primary media consumption endpoint for LAN and Tailnet clients

This document describes the current containerized media services running on VM100 (Compute/GPU VM).

## Runtime Characteristics

- VMID: 100
- Hostname: GPU
- OS: Ubuntu 22.04.5 LTS
- Cores: 8 (1 socket)
- RAM: 16384 MB
- System disk: 64 GB (local-lvm, SSD, discard + iothread)
- Aux disk: a few hundred GB (aux data pool — Docker data-root, per the aux-disk convention)
- SCSI controller: virtio-scsi-single
- BIOS / machine: OVMF (UEFI) / q35
- GPU passthrough: NVIDIA GPU via `hostpci0` (PCIe, primary VGA)
- Guest agent: enabled
- Onboot: yes
- Startup order: 6 (40s up-delay)

## Jellyfin

- Deployment: Docker Compose (`/opt/docker/jellyfin/docker-compose.yml` on VM100)
- GPU acceleration: enabled (`gpus: all` + NVIDIA environment variables)
- Runs as non-root user (`user: 1000:1000`)
- Persistent application data:
  - `${JF_CONFIG}` → `/config`
  - `${JF_CACHE}` → `/cache`
  - `${JF_METADATA}` → `/metadata`
- Media mounts (read-only, least privilege):
  - `${JF_MEDIA_FILME}` → `/media/Filme:ro`
  - `${JF_MEDIA_SERIEN}` → `/media/Serien:ro`
- Port exposure: `8096/TCP` (LAN)
- See: [Jellyfin Service](../services/jellyfin.md)

## Audiobookshelf

- Deployment: Docker Compose (`/opt/docker/audiobookshelf/docker-compose.yml` on VM100)
- Media mounts (read-only, least privilege):
  - `${ABS_AUDIOBOOKS_ROOT}` → `/audiobooks:ro`
  - `${ABS_PODCASTS_ROOT}` → `/podcasts:ro`
- Port exposure: `13378/TCP` (LAN)
- See: [Audiobookshelf Service](../services/audiobookshelf.md)

## Ollama

- Installation: native systemd service
- Override: `/etc/systemd/system/ollama.service.d/override.conf`
- Bind address: Tailscale IP only (`<tailscale-ip-vm100>:11434`)
- Model: `qwen3-8b-16k` (Q4_K_M quantization; see [Ollama Service](../services/ollama.md))
- Role: backup inference backend for OpenWebUI (CT230)
- See: [Ollama Service](../services/ollama.md)

## Storage Mount Strategy (Reboot-Safe)

Media paths on VM100 are provided via **systemd automount** units (fstype `autofs`) to ensure reboot-safe startup behavior:
- Jellyfin media path (referenced by `${JF_MEDIA_*}` variables)
- Audiobookshelf media path (referenced by `${ABS_*_ROOT}` variables)

Note: A legacy `media-mergerfs.mount` unit exists on VM100 but is not used for service mounts in the current state.

## aux-disk Storage Status (2026-06-25)

VM100's second disk — the `jellyfin-data` image (`scsi1`, an ext4 `.raw` stored on
the Proxmox host's aux-disk) — was hosted on the failing aux-disk disk. aux-disk suffered
unrecoverable medium errors and is being decommissioned (see
[KE-13](../platform/known-errors.md#ke-13-aux-disk-physical-disk-failure-medium-errors)).

- **Jellyfin** config/cache/metadata (`${JF_CONFIG}`/`${JF_CACHE}`/`${JF_METADATA}`
  → `/mnt/vm-data/jellyfin`) lived on this image and was **rescued read-only**
  (`jf-jellyfin.tar`, including `jellyfin.db` + artwork). No re-scrape needed.
- **Audiobookshelf** data (`${ABS_DATA_ROOT}` = `/opt/docker/audiobookshelf`) lives
  on the VM100 **root** disk (local-lvm), **not** on aux-disk — unaffected; backed up
  as a precaution.
- VM100 and the Jellyfin stack are **down** until the jellyfin-data image is
  relocated onto healthy storage. Full context:
  [incident write-up](../platform/incidents/2026-06-25-aux-disk-failure-and-recovery.md).

## Network / Tailscale
- Tailscale hostname: gpu-vm
- Tag: `tag:tier2`
- Accessible by: `tag:admin` (all ports), `tag:tier0` (all ports), `tag:tier2` (all ports), `tag:ai-stack` (port 11434), `tag:monitoring` (ports 9100, 8096, 13378 — node_exporter + blackbox probes), `tag:client` (ports 443, 8096, 13378), `tag:untrusted` (ports 443, 8096, 13378)

### Tailscale Serve

Not in use. Jellyfin and Audiobookshelf bind to `0.0.0.0` for LAN streaming performance.
Remote access uses the Tailscale IP directly (WireGuard-encrypted, no TLS hostname).

See: [Loopback + Tailscale Serve ADR](../decisions/loopback-tailscale-serve.md) — section "Documented Exceptions"

## Security / Exposure Notes (Trade-off)

- No public reverse proxy and no router port-forwarding.
- Default remote access path is Tailscale (identity-based overlay).
- Network policy enforcement is defined via Tailscale ACL (tags + JSON policy).
  See: [docs/platform/tailscale-acl.md](../platform/tailscale-acl.md)

### Intentional LAN Exposure

- Jellyfin (`8096/TCP`) and Audiobookshelf (`13378/TCP`) are intentionally reachable on the LAN.
- This is a documented performance trade-off (bandwidth/latency optimization and reduced transcoding load).
- LAN exposure must remain limited to these specific ports only.

### Unintentional LAN Exposure — sshd binds `0.0.0.0:22` (open)

`sshd -T` reports `listenaddress 0.0.0.0:22` and `[::]:22`. Port 22 is therefore reachable on the
LAN, which the rule above does not permit, and which the platform binding rule ("services bind to
the Tailscale IP, or to loopback behind `tailscale serve`; never to LAN interfaces") forbids.
LXC250 does this correctly, pinning `ListenAddress` to its Tailscale IP.

Until 2026-07-09 this was combined with `PasswordAuthentication yes` (see Configuration
Management above). Password authentication is now off, so the acute risk is closed and only
key-based access remains — but the bind is still wrong.

Not fixed. Pinning `ListenAddress` to the Tailscale IP couples sshd's startup to `tailscaled`
having assigned that address, which is the KE-9 / KE-12 boot-race class and the documented reason
LXC250 is unreachable over SSH for 30–60 s after boot. Whether the `ssh_hardening` role should own
`ListenAddress` at all — and whether an `ExecStartPre` wait or a `postgresql_boot_order`-style
drop-in is the right mechanism — is a design decision, not a line to add to an unrelated pass.

## Failure Impact

If VM100 becomes unavailable:

- No media streaming (Jellyfin, Audiobookshelf)
- No GPU-accelerated workloads
- Storage layer (VM102) is NOT affected
- No data loss (media is read-only from SMB storage)
- Recovery: restart VM, verify mounts, confirm Docker containers are running

## Time Synchronization

- `chrony` keeps the system clock synchronized (verify: `chronyc tracking`, `chronyc sources`, `timedatectl`).
- Why it matters here: cross-node log correlation during incidents (see KE-8), and a consistent time source across the VM fleet.
- Before 2026-06-08 vm100 used `systemd-timesyncd` (the Debian default) and was already synced — it was never the gap. The `chrony` role replaced timesyncd fleet-wide for a single, consistent time daemon across both VMs; the `chrony` package `Conflicts:` with `systemd-timesyncd`, so apt removed timesyncd on install.
- LXCs do not run their own time daemon — they inherit the Proxmox host clock; this concern applies to VMs only.

## Configuration Management

Managed via Ansible from LXC250.

- **Playbook:** `ansible/playbooks/apt-upgrade.yml` — rolling apt upgrade (`serial: 1`)
- **Role:** `ansible/roles/node_exporter/` — deploys node_exporter binary + systemd unit
- **Role:** `ansible/roles/ssh_hardening/` — `PasswordAuthentication no`, `PermitRootLogin no`, applied live 2026-07-09 via the `00-hardening.conf` drop-in. Until that date this node was effectively **unhardened**: the role wrote the directives into `/etc/ssh/sshd_config`, but `Include sshd_config.d/*.conf` is expanded earlier in that file and cloud-init's `50-cloud-init.conf` had already set `PasswordAuthentication yes` — sshd honours the *first* match. Verified with `sshd -T` (effective config), not by reading `sshd_config`.
- **Role:** `ansible/roles/chrony/` — installs `chrony`, ensures started + enabled (replaced `systemd-timesyncd`)
- **Role:** `ansible/roles/breakglass/` — deploys the admin break-glass pubkey (`admin-workstation`) to the native `gpu` user (`breakglass_user: gpu`)
- **SSH access model:** primary admin path is the `ansible` user (key-based, NOPASSWD sudo). Break-glass fallback: the `gpu` user's `authorized_keys` holds the admin workstation key (`admin-workstation`), codified 2026-06-08 via the `breakglass` role. `PasswordAuthentication no`, so key presence is the only access lever. VMs need an SSH break-glass because out-of-band `qm guest exec` depends on the qemu-guest-agent; LXCs are reachable via `pct exec` and need none.
- **Role:** `ansible/roles/docker_compose_update/` (playbook `ansible/playbooks/docker-compose-update.yml`, group `docker`) — updates this node's two Compose stacks (`/opt/docker/audiobookshelf`, `/opt/docker/jellyfin`) via `docker_compose_v2`: `pull: always` + `recreate: auto` (idempotent — recreates only on image/config change). The list var `compose_projects` in `host_vars/vm100.yml` iterates both, one stack at a time.
- **Role:** `ansible/roles/jellyfin_watchdog/` — deploys `jellyfin-cuda-watchdog.sh` and its monotonic timer (`OnBootSec=5min`, `OnUnitActiveSec=30min`). Adopted 2026-07-10; previously a hand-written `*/30 * * * *` root crontab entry, which the role removed. The node's root crontab is now empty.
- **Role:** `ansible/roles/unattended_upgrades/` — restricts `unattended-upgrades` to the security pockets and blacklists kernel + NVIDIA packages, so a DKMS/NVIDIA break cannot land unattended on a GPU node. The origin ids are Ubuntu-specific, hence `hosts: vm100` rather than a group.
- **Role:** `ansible/roles/systemd_hygiene/` — removes the stale hand-written `media-mergerfs.mount` unit (legacy, no consumer; Jellyfin reads storage over CIFS).

See: [Ansible Platform](../platform/ansible.md)

## Scheduled Tasks

All scheduled work runs from systemd timers; the root crontab is intentionally empty.
A failed timer run raises the fleet-wide `SystemdUnitFailed` alert — cron jobs failed silently.

- `jellyfin-cuda-watchdog.timer` — polls `nvidia-smi` inside the Jellyfin container and restarts
  it on CUDA loss (see [Known Errors](../platform/known-errors.md), KE-10).
  Monotonic, not calendar-based: `Persistent=` would be meaningless, since a poll missed while the
  host was off has nothing to catch up on.
  Inspect: `systemctl list-timers jellyfin-cuda-watchdog.timer`, `journalctl -t jellyfin-cuda-watchdog`
