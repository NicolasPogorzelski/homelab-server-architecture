# VM100 Services (GPU / Media)

## Purpose

- GPU-accelerated media streaming (Jellyfin with NVIDIA hardware transcoding)
- Audiobook hosting (Audiobookshelf)
- Local LLM inference backend (`llama-server`, the always-on fallback for the AI stack)
- Primary media consumption endpoint for LAN and Tailnet clients

This document describes the current containerized media services running on VM100 (Compute/GPU VM).

## Runtime Characteristics

- VMID: 100
- Hostname: GPU
- OS: Ubuntu 22.04.5 LTS
- Cores: 8 (1 socket)
- RAM: 16384 MB
- System disk: 64 GB (local-lvm, SSD, discard + iothread)
- Aux disk: a few hundred GB, mounted at `/mnt/vm-data` - application data, LLM models, Docker's
  data root (`/mnt/vm-data/docker`, measured with `docker info` on 2026-10-01). 28 G of 295 G used
  after the Ollama models and the benchmark leftovers were removed that day
- NVIDIA driver: 580.178.04 (`nvidia-driver-580-server`, CUDA 13.0), replacing 535 on 2026-09-29
- SCSI controller: virtio-scsi-single
- BIOS / machine: OVMF (UEFI) / q35
- GPU passthrough: NVIDIA GPU via `hostpci0` (PCIe, primary VGA)
- Guest agent: enabled
- Onboot: yes
- Startup order: 6 (40s up-delay)

## Jellyfin

- Deployment: Docker Compose (`/opt/docker/jellyfin/docker-compose.yml` on VM100)
- GPU acceleration: enabled (`gpus: all` + NVIDIA environment variables)
- Runs as non-root user (`user: 1000:1000`)
- Persistent application data:
  - `${JF_CONFIG}` -> `/config`
  - `${JF_CACHE}` -> `/cache`
  - `${JF_METADATA}` -> `/metadata`
- Media mounts (read-only, least privilege):
  - `${JF_MEDIA_FILME}` -> `/media/Filme:ro`
  - `${JF_MEDIA_SERIEN}` -> `/media/Serien:ro`
- Port exposure: `127.0.0.1:8096`, tailnet through `tailscale serve --tcp 8096`
- See: [Jellyfin Service](../services/jellyfin.md)

## Audiobookshelf

- Deployment: Docker Compose (`/opt/docker/audiobookshelf/docker-compose.yml` on VM100)
- Media mounts (read-only, least privilege):
  - `${ABS_AUDIOBOOKS_ROOT}` -> `/audiobooks:ro`
  - `${ABS_PODCASTS_ROOT}` -> `/podcasts:ro`
- Port exposure: `127.0.0.1:13378`, tailnet through `tailscale serve --tcp 13378`
- See: [Audiobookshelf Service](../services/audiobookshelf.md)

## llama-server

- Deployment: Docker Compose (`/opt/docker/llama-server/`), CUDA 12 image `server-cuda-b11243`
- Router mode: no model loaded after start, loaded on the first request, unloaded after 20 minutes
  idle, so Jellyfin has the whole card whenever nobody is asking
- Model: `qwen3.5-9b` (Q4_K_M, text only) from `/mnt/vm-data/models`, 32K context, 5.8 GB of
  VRAM when loaded, one slot
- CUDA kernel cache in `/mnt/vm-data/cuda-cache`, so a recreated container does not rebuild it
- Listens on `127.0.0.1:8080`; the tailnet reaches it through `tailscale serve --tcp 8080`
- Replaced the native Ollama 0.19 service, removed on 2026-10-01 after OpenWebUI had switched: unit
  and drop-in, `/usr/local/bin/ollama`, `/usr/local/lib/ollama`, the `ollama` user and group, and
  15 GB of models under `/mnt/vm-data/ollama`. The benchmark directory `/mnt/vm-data/llmtest` from
  2026-09-29 (19 GB) went with it
- See: [LLM Inference](../services/llm-inference.md)

## Storage Mount Strategy (Reboot-Safe)

Media paths are provided via systemd automount units (fstype `autofs`), so a mount is attempted on
first access rather than once at boot - the KE-15 failure class. Four units since 2026-08-16, one
per library:

| Unit | Mountpoint | Share on VM102 | Consumed via |
|---|---|---|---|
| `srv-media-filme.automount` | `/srv/media/filme` | `media-jf-filme` | `${JF_MEDIA_FILME}` |
| `srv-media-serien.automount` | `/srv/media/serien` | `media-jf-serien` | `${JF_MEDIA_SERIEN}` |
| `srv-media-audiobooks.automount` | `/srv/media/audiobooks` | `media-abs-audiobooks` | `${ABS_AUDIOBOOKS_ROOT}` |
| `srv-media-podcasts.automount` | `/srv/media/podcasts` | `media-abs-podcasts` | `${ABS_PODCASTS_ROOT}` |

All four mount read-only (`ro`) over VM102's LAN address, which is the documented exception in
[SMB Bind and LAN Access](../decisions/smb-bind-and-lan-access.md), not an oversight. They replaced
two pool-wide mounts (`media-jellyfin`, `media-audiobookshelf`) that exported the entire MergerFS
pool to each consumer; the narrower shares put the boundary where it is evaluated first, ahead of
any filesystem permission.

The four superseded units were disabled rather than unmounted, because unmounting a live CIFS mount
on this node is what froze the guest in [KE-20](../platform/known-errors.md#ke-20). The nightly
power-off retired them; their removal is owned by the `systemd_hygiene` role
(`inventory/host_vars/vm100.yml`) rather than done by hand, so it survives a rebuild of this node.
The same role removes the legacy `media-mergerfs.mount`.

## aux-disk Storage Status (2026-06-25)

VM100's second disk - the `jellyfin-data` image (`scsi1`, an ext4 `.raw` stored on
the Proxmox host's aux-disk) - was hosted on the failing aux disk. aux-disk suffered
unrecoverable medium errors and is being decommissioned (see
[KE-13](../platform/known-errors.md#ke-13-aux-disk-physical-disk-failure-medium-errors)).

- **Jellyfin** config/cache/metadata (`${JF_CONFIG}`/`${JF_CACHE}`/`${JF_METADATA}`
  -> `/mnt/vm-data/jellyfin`) lived on this image and was rescued read-only
  (`jf-jellyfin.tar`, including `jellyfin.db` + artwork). No re-scrape needed.
- **Audiobookshelf** data (`${ABS_DATA_ROOT}` = `/opt/docker/audiobookshelf`) lives
  on the VM100 root disk (local-lvm), not on aux-disk - unaffected; backed up
  as a precaution.

Full context: [incident write-up](../platform/incidents/2026-06-25-aux-disk-failure-and-recovery.md).

**Current state, measured 2026-08-17.** The paragraph above describes the incident, and until
this date the section closed by saying that VM100 and the Jellyfin stack "are down until the
jellyfin-data image is relocated onto healthy storage". That has not been true for weeks: the VM
runs and the Jellyfin container reports `healthy`. What *is* still true is the half that mattered -
the image was never relocated. `qm config 100` reads
`scsi1: appdata_aux-disk:100/vm-100-disk-0.raw,size=300G`, so the second disk remains a raw file
on directory storage on the KE-13 disk.

Two consequences follow from that and are easy to miss because the node looks healthy:

- Nothing on that disk has an off-site copy, and its 7680 unreadable sectors are unchanged.
- A raw file on directory storage cannot be snapshotted, so this VM has no rollback path at all
  (see the note in `CLAUDE.md`). That is the precondition blocking any non-trivial maintenance
  here, including the [KE-20](../platform/known-errors.md#ke-20) investigation.

The lesson is about the sentence rather than the disk: an incident status written in the present
tense keeps asserting itself long after it stops being true, and it reads as current to anyone who
arrives at the file later. Incident state belongs in the incident write-up with its date; a node
document should carry the configuration that is live now.

## Network / Tailscale
- Tailscale hostname: gpu-vm
- Tag: `tag:tier2`
- Accessible by: `tag:monitoring` (9100, 8096, 13378, 8080 - node_exporter + blackbox probes), `tag:control` (22), `tag:admin` (22, 8096, 13378), `tag:ai-stack` (8080), `tag:admin-mobile` and `tag:client` (8096, 13378), `tag:reader` (13378), `tag:untrusted` and `tag:media-player` (8096), and one external user through machine sharing (8096, 13378) ([ACL model](../platform/tailscale-acl.md), rebuilt 2026-09-26)

### Tailscale Serve

Three TCP forwards, so no service waits for the Tailscale address at boot:

| Service | Tailnet port | Backend |
|---|---|---|
| `llama-server` | 8080 | `tcp://127.0.0.1:8080` |
| Jellyfin | 8096 | `tcp://127.0.0.1:8096` (since 2026-10-01) |
| Audiobookshelf | 13378 | `tcp://127.0.0.1:13378` (since 2026-10-01) |

Set by hand with `tailscale serve --bg --tcp <port> tcp://127.0.0.1:<port>`; `tailscaled` keeps the
configuration in its state across reboots. `tailscale serve status` lists all three. Plain TCP, so
no TLS hostname; the tunnel is WireGuard-encrypted.

See: [Loopback + Tailscale Serve ADR](../decisions/loopback-tailscale-serve.md)

## Security / Exposure Notes (Trade-off)

- No public reverse proxy and no router port-forwarding.
- Default remote access path is Tailscale (identity-based overlay).
- Network policy enforcement is defined via Tailscale ACL (tags + JSON policy).
  See: [docs/platform/tailscale-acl.md](../platform/tailscale-acl.md)

### No Media Ports on the LAN

Jellyfin and Audiobookshelf were reachable on the LAN until 2026-10-01, as the trade-off in
[DD#8](../decisions/design-decisions.md#dd-8). Both now publish on loopback only. The trade-off
rested on the internet uplink limiting streams through the overlay; measured on 2026-10-01, two
tailnet nodes on the same LAN connect directly (`tailscale ping` 1 ms, via the LAN address) and an
SMB transfer reached 95 MB/s, so the uplink plays no part. The last LAN client, the streaming box,
moved to the tailnet the same day ([ACL Rule 14](../platform/tailscale-acl.md#rule-14---media-player-the-streaming-box-at-the-tv)).

### No IPv6 Address on the LAN Interface

`enp6s18` accepts no router advertisements since 2026-10-01, so it holds no global or ULA IPv6
address, only its link-local one. Until then `systemd-networkd` built both from the router's
advertisements, although the netplan file mentions only `dhcp4`, and Jellyfin, Audiobookshelf and
sshd listened on `[::]` behind a world-routable address that only the router's inbound IPv6 policy
kept closed. The listeners still read `[::]`; nothing outside the host can address them over IPv6.
The tailnet's IPv6 address sits on `tailscale0` and is unaffected.

- Source: `/etc/netplan/60-no-ipv6-ra.yaml`, `accept-ra: false` for `enp6s18`, mode 0600, applied
  with `netplan try`. A separate file, because `50-cloud-init.yaml` belongs to cloud-init and was
  rewritten at the boot of 2026-10-01 (mtime 07:16). Applied by hand, not yet owned by a role.
- Verified 2026-10-01: `ip -6 addr show dev enp6s18` lists only `fe80::`, IPv4 unchanged, all seven
  blackbox probes at 1. Held across the cold boot of 2026-10-02.
- Rollback: `rm /etc/netplan/60-no-ipv6-ra.yaml && netplan apply`; the pre-change directory is kept
  at `/root/netplan.bak-20261001`.

### Unintentional LAN Exposure - sshd binds `0.0.0.0:22` (open)

`sshd -T` reports `listenaddress 0.0.0.0:22` and `[::]:22`. Port 22 is therefore reachable on the
LAN, which the rule above does not permit, and which the platform binding rule ("services bind to
the Tailscale IP, or to loopback behind `tailscale serve`; never to LAN interfaces") forbids.
LXC250 does this correctly, pinning `ListenAddress` to its Tailscale IP.

Until 2026-07-09 this was combined with `PasswordAuthentication yes` (see Configuration
Management above). Password authentication is now off, so the acute risk is closed and only
key-based access remains - but the bind is still wrong.

Not fixed. Pinning `ListenAddress` to the Tailscale IP couples sshd's startup to `tailscaled`
having assigned that address, which is the KE-9 / KE-12 boot-race class and the documented reason
LXC250 is unreachable over SSH for 30-60 s after boot. Whether the `ssh_hardening` role should own
`ListenAddress` at all - and whether an `ExecStartPre` wait or a `postgresql_boot_order`-style
drop-in is the right mechanism - is a design decision, not a line to add to an unrelated pass.

## Failure Impact

If VM100 becomes unavailable:

- No media streaming (Jellyfin, Audiobookshelf)
- No GPU-accelerated workloads
- Storage layer (VM102) is NOT affected
- No data loss (media is read-only from SMB storage)
- Recovery: restart VM, verify mounts, confirm Docker containers are running

## Time Synchronization

- `chrony` keeps the system clock synchronized (verify: `chronyc tracking`, `chronyc sources`, `timedatectl`).
- Why it matters here: cross-node log correlation during incidents (see KE-8), and a consistent time source across the VM fleet.
- Before 2026-06-08 vm100 used `systemd-timesyncd` (the Debian default) and was already synced - it was never the gap. The `chrony` role replaced timesyncd fleet-wide for a single, consistent time daemon across both VMs; the `chrony` package `Conflicts:` with `systemd-timesyncd`, so apt removed timesyncd on install.
- LXCs do not run their own time daemon - they inherit the Proxmox host clock; this concern applies to VMs only.

## Configuration Management

Managed via Ansible from LXC250.

- **Playbook:** `ansible/playbooks/apt-upgrade.yml` - rolling apt upgrade (`serial: 1`)
- **Role:** `ansible/roles/node_exporter/` - deploys node_exporter binary + systemd unit
- **Role:** `ansible/roles/ssh_hardening/` - `PasswordAuthentication no`, `PermitRootLogin no`, applied live 2026-07-09 via the `00-hardening.conf` drop-in. Until that date this node was effectively unhardened: the role wrote the directives into `/etc/ssh/sshd_config`, but `Include sshd_config.d/*.conf` is expanded earlier in that file and cloud-init's `50-cloud-init.conf` had already set `PasswordAuthentication yes` - sshd honours the *first* match. Verified with `sshd -T` (effective config), not by reading `sshd_config`.
- **Role:** `ansible/roles/chrony/` - installs `chrony`, ensures started + enabled (replaced `systemd-timesyncd`)
- **Role:** `ansible/roles/breakglass/` - deploys the admin break-glass pubkey (`admin-workstation`) to the native `gpu` user (`breakglass_user: gpu`)
- **SSH access model:** primary admin path is the `ansible` user (key-based, NOPASSWD sudo). Break-glass fallback: the `gpu` user's `authorized_keys` holds the admin workstation key (`admin-workstation`), codified 2026-06-08 via the `breakglass` role. `PasswordAuthentication no`, so key presence is the only access lever. VMs need an SSH break-glass because out-of-band `qm guest exec` depends on the qemu-guest-agent; LXCs are reachable via `pct exec` and need none.
- **Role:** `ansible/roles/docker_compose_update/` (playbook `ansible/playbooks/docker-compose-update.yml`, group `docker`) - updates this node's two Compose stacks (`/opt/docker/audiobookshelf`, `/opt/docker/jellyfin`) via `docker_compose_v2`: `pull: always` + `recreate: auto` (idempotent - recreates only on image/config change). The list var `compose_projects` in `host_vars/vm100.yml` iterates both, one stack at a time.
- **Role:** `ansible/roles/jellyfin_watchdog/` - deploys `jellyfin-cuda-watchdog.sh` and its monotonic timer (`OnBootSec=5min`, `OnUnitActiveSec=30min`). Adopted 2026-07-10; previously a hand-written `*/30 * * * *` root crontab entry, which the role removed. The node's root crontab is now empty.
- **Role:** `ansible/roles/unattended_upgrades/` - restricts `unattended-upgrades` to the security pockets and blacklists kernel + NVIDIA packages, so a DKMS/NVIDIA break cannot land unattended on a GPU node. The origin ids are Ubuntu-specific, hence `hosts: vm100` rather than a group.
- **Role:** `ansible/roles/docker_mount_ordering/` (playbook
  `ansible/playbooks/docker-mount-ordering.yml`) - orders `docker.service` after the four media
  automount units. Without it, Docker can bind `/srv/media/*` before autofs has installed its
  trigger there, and the container then serves an empty directory on the local root filesystem while
  every health signal stays green. The drop-in names the `.automount` units, never the `.mount`
  units: an automount is up in milliseconds whether or not VM102 is reachable, while ordering after
  the mount itself would tie this node's Docker daemon to a remote host being up - the KE-15 class,
  rebuilt by hand. `Wants=`, not `Requires=`, for the same reason.
- **Role:** `ansible/roles/docker_boot_retry/` (playbook
  `ansible/playbooks/docker-boot-retry.yml`) - starts, once per boot, a container whose start
  failed. The ordering above guarantees a trigger, not a mount: runc binding `/srv/media/filme`
  sets off the one CIFS mount attempt, and if that attempt fails the start fails with `no such
  device`. `unless-stopped` does not apply, because Docker restarts only containers that once ran,
  and the CUDA watchdog skips stopped containers by design. Retry: six passes, 30 s apart, only for
  containers with a `State.Error`, so `docker stop` is respected.
  - **2026-09-29, 10:19 boot:** vm102 unreachable (`cifs_mount failed w/return code = -113`,
    `EHOSTUNREACH`). Jellyfin and Audiobookshelf both stayed down; the mounts were brought up by
    hand at 10:26 and the incident was not recorded at the time.
  - **2026-10-03, 09:02 boot:** `Send error in SessSetup = -11` (`EAGAIN`) on the film share. smbd
    on vm102 had been up since 08:59:33 and logged nothing for vm100, so the refusal came from
    vm100's own CIFS client. The audiobook mount started 12 ms earlier. Working explanation, not
    proven: the client multiplexes all mounts to one server over a single TCP connection, and the
    session setup for `media-jf` collided with the one for `media-abs` still in progress. Possible
    only since 2026-08-16, when two shared shares became four scoped ones under two users; first
    occurrence in the 121 boots the journal holds (since 2026-05-16).
  - The journal holds two earlier instances with a third trigger, the NVIDIA prestart hook timing
    out (2026-08-05, 2026-08-24). All four are in [KE-27](../platform/known-errors.md#ke-27).
- **Role:** `ansible/roles/netconsole/` (playbook `ansible/playbooks/netconsole.yml`) - streams the
  kernel log over UDP to a receiver on the Proxmox host, so a freeze that stops disk writes still
  leaves evidence. Written after [KE-20](../platform/known-errors.md#ke-20), where this node wedged
  and journald recorded nothing at all. The role also raises `console_loglevel` to 7 via
  `/etc/sysctl.d/60-netconsole-printk.conf`: the stock 4 filters `INFO: task blocked for more than
  120 seconds`, the one message a hung-task investigation needs. The module is loaded from a unit
  ordered `After=network-online.target`, not from `/etc/modules-load.d/` - that runs before the
  interface has an address, and the resulting failure would be silent. The target is the host's LAN
  address because netpoll writes frames from inside the kernel; a Tailscale address lives on a TUN
  device served by a userspace daemon, which is frozen along with everything else at the moment this
  channel matters.
- **Role:** `ansible/roles/systemd_hygiene/` - removes the stale hand-written `media-mergerfs.mount` unit (legacy, no consumer; Jellyfin reads storage over CIFS).

See: [Ansible Platform](../platform/ansible.md)

## Scheduled Tasks

All scheduled work runs from systemd timers; the root crontab is intentionally empty.
A failed timer run raises the fleet-wide `SystemdUnitFailed` alert - cron jobs failed silently.

- `jellyfin-cuda-watchdog.timer` - polls `nvidia-smi` inside the Jellyfin container and restarts
  it on CUDA loss (see [Known Errors](../platform/known-errors.md), KE-10).
  Monotonic, not calendar-based: `Persistent=` would be meaningless, since a poll missed while the
  host was off has nothing to catch up on.
  Inspect: `systemctl list-timers jellyfin-cuda-watchdog.timer`, `journalctl -t jellyfin-cuda-watchdog`
