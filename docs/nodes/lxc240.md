# LXC240 - Vaultwarden

This document describes the Vaultwarden container (LXC240).

## Purpose

- Self-hosted password manager (Bitwarden-compatible)
- Security-critical service (secrets tier)

## Runtime Characteristics

- CTID: 240
- Hostname: vaultwarden
- OS: Debian 12 (bookworm)
- Cores: 2
- RAM: 1024 MB
- Swap: 512 MB
- Root disk: 8 GB (local-lvm)
- Unprivileged: yes
- Nesting: enabled
- Onboot: yes
- Startup order: 4 (after storage + monitoring + nextcloud, 20s delay)

## Mount Points

- `mp0`: `/mnt/smb/vaultwarden` -> `/opt/vaultwarden` (persistent data on SMB storage)

## LXC Configuration

Tailscale TUN configuration (CT210-pattern, see [DD#13](../decisions/design-decisions.md#13-standardized-tun-configuration-for-tailscale-capable-lxcs)):

    lxc.cgroup2.devices.allow: c 10:200 rwm
    lxc.mount.entry: /dev/net/tun dev/net/tun none bind,create=file

## Network / Tailscale

- Tailscale hostname: vaultwarden
- Tag: `tag:tier1`
- Accessible by: `tag:admin` (all ports), `tag:tier0` (all ports), `tag:tier1` (all ports), `tag:client` (port 443)

## Security / Exposure

- Classified as tier 1 (security-critical)
- Loopback-only binding (`127.0.0.1:8080`)
- No LAN exposure
- No public exposure / no router port forwarding
- Remote access provided exclusively via Tailscale (identity-based overlay)
- Network policy enforced via Tailscale ACL (node tags + ACL JSON)
- See: [docs/platform/tailscale-acl.md](../platform/tailscale-acl.md)
- LXC TUN config follows CT210-pattern (DD#13)

## Failure Impact

If LXC240 becomes unavailable:

- No access to password vault
- Clients with cached credentials continue to work temporarily
- SQLite database and encryption keys become inaccessible
- Recovery: recreate LXC, remount storage, redeploy Docker container

**Backup state, stated rather than assumed (2026-08-17).** This section used to close with
"Backups of database and key material are critical", which is a judgement about importance, not a
record of what exists. What exists: nothing but SnapRAID parity. Per
[`data-classification.md`](../platform/data-classification.md) this vault is C1 - the highest class
on the platform, holding every household credential - and its protection column reads "Parity only.
No export, no versions." Parity defends against losing a disk; it does not defend against deletion,
corruption or ransomware, because the next `snapraid sync` writes the damage into the parity.

Two consequences worth keeping in view. The SQLite file lives on a CIFS mount
([KE-5](../platform/known-errors.md#ke-5)), so copying it while Vaultwarden is running is a gamble
on timing rather than a backup. And its `-shm`/`-wal` side files were captured by parity at a
different moment than the main database until [KE-19](../platform/known-errors.md#ke-19) excluded
them on 2026-08-15 - `db.sqlite3` itself deliberately stays in the array, because imperfect
protection beats none until a real export exists.

A consistent export is the last open half of Tier 1 #3 in the
[remediation plan](../platform/remediation-plan.md).

## Configuration Management

Managed via Ansible from LXC250.

- **Stack path:** `/opt/vaultwarden/compose/` - active Compose stack; intentionally outside the repo clone
- **Playbook:** `ansible/playbooks/apt-upgrade.yml` - rolling apt upgrade (`serial: 1`)
- **Role:** `ansible/roles/node_exporter/` - deploys node_exporter binary + systemd unit
- **Role:** `ansible/roles/ssh_hardening/` - `PasswordAuthentication no`, `PermitRootLogin no`
- **Role:** `ansible/roles/docker_compose_update/` (playbook `ansible/playbooks/docker-compose-update.yml`, group `docker`) - updates the node's Compose stack(s) via `docker_compose_v2`: `pull: always` + `recreate: auto` (idempotent - recreates only on image/config change). Stack dir `/opt/vaultwarden/compose` in `host_vars/lxc240.yml` (`compose_projects`); the compose file pins `name: vaultwarden` so the project name stays stable despite the `compose` dir basename.

See: [Ansible Platform](../platform/ansible.md)
