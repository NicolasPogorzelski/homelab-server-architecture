# VM102 - Storage

This document describes the dedicated storage VM (VM102).

VM102 is the single source of truth for all persistent data in the infrastructure.

## Purpose

- SnapRAID parity-based data protection
- MergerFS unified namespace across data disks
- Samba exports with per-service identity segmentation
- Centralized storage for all service containers and VMs

## Runtime Characteristics

- VMID: 102
- Hostname: Storage
- OS: Debian 12 (bookworm)
- Cores: 2 (1 socket)
- RAM: 4096 MB
- System disk: 16 GB (local-lvm, virtio-scsi-single)
- SCSI controller: virtio-scsi-single
- Guest agent: enabled
- Onboot: yes
- Startup order: 1 (first after hypervisor, 30s delay)

## Disk Topology

### System Disk

- `scsi0`: local-lvm - OS + swap

### Data Disks (SnapRAID)

- `scsi1`-`scsi5`: 5 data disks (disk01-disk05)

### Parity Disk

- `scsi6`: 1 parity disk (must be >= largest data disk)

### Auxiliary Disks (non-parity)

- `scsi7`: aux-disk

> **`scsi8` removed 2026-07-09.** The disk formerly attached here (`aux-disk1`) now lives on the
> Proxmox host, mounted `rw` at `/mnt/aux-disk` as the Docker data-root store for LXC200/211/220/230/260
> and as the backing store for VM100's `scsi1`. It had remained passed through to this VM as well,
> so the same ext4 filesystem was reachable from two kernels; VM102's fstab entry was commented out,
> which is the only reason no corruption occurred. The passthrough is gone and VM102's fstab now
> carries an explicit do-not-mount warning. See
> [KE-13](../platform/known-errors.md#ke-13-aux-disk-physical-disk-failure-medium-errors).

All data and parity disks are passed through via `/dev/disk/by-id/` on the hypervisor for deterministic mapping.
Exact models and capacities are documented offline.

## Monitoring

- Node Exporter v1.11.1 (systemd binary, `/etc/systemd/system/node_exporter.service`)
- Binds to Tailscale IP only (`--web.listen-address=<tailscale-ip-vm102>:9100`)
- Textfile collector enabled (`--collector.textfile.directory=/var/lib/node_exporter/textfile_collector`)
- systemd collector enabled - exports `node_systemd_unit_state`, feeding `SystemdUnitFailed`
- Textfile metrics written by `/usr/local/sbin/snapraid-maintenance.sh`:
  - `snapraid_sync.prom` - timestamp of last successful sync
  - `snapraid_scrub.prom` - timestamp of last successful scrub
- systemd timers (`snapraid_maintenance` role; replaced `/etc/cron.d/snapraid` on 2026-07-10):
  - `snapraid-sync.timer` -> `snapraid-maintenance@sync.service` - daily at 23:00
  - `snapraid-scrub.timer` -> `snapraid-maintenance@scrub.service` - monthly, 1st at 20:00
  - Both `Persistent=true`: the host is often powered down before 23:00, and the cron
    entries were skipped on those nights with no retry and no signal
- Prometheus alert rules: `SnapRAIDSyncStale` (>26h), `SnapRAIDScrubStale` (>32d)

## Time Synchronization

- `chrony` keeps the system clock synchronized (verify: `chronyc tracking`, `chronyc sources`, `timedatectl`).
- Why it matters here: a storage node's clock underpins SnapRAID change detection (timestamp + size based), backup correctness, the `SnapRAIDSyncStale` alert math, and cross-node log correlation during incidents.
- Before 2026-06-07 no time daemon was installed (`timedatectl`: `NTP service: n/a`, `synchronized: no`); the clock relied on RTC/hypervisor only and drifted. `chrony` installed + enabled; `timedatectl` now reports `synchronized: yes`.
- Originally installed ad-hoc; codified 2026-06-08 into the fleet-wide `chrony` role (`ansible/roles/chrony/`, applied to `vms`).
- LXCs do not run their own time daemon - they inherit the Proxmox host clock; this concern applies to VMs (vm100 was already synced, vm102 was the gap).

- MergerFS pool at `/mnt/mergerfs` (unified view of disk01-disk05 + aux-disk temporary capacity bridge)
- SnapRAID with single parity (manual sync + scrub)
- Samba exports with per-service users and least-privilege enforcement

## Security / Exposure

- Samba (port 445) is the only service exposed to other nodes
- SMB3 only, mandatory signing
- No router port forwarding
- Network policy enforced via Tailscale ACL (node tags + ACL JSON)
- See: [docs/platform/tailscale-acl.md](../platform/tailscale-acl.md)

### SMB boundary is enforced in the kernel, not by Samba's bind (2026-07-14)

`smbd` listens on `0.0.0.0:445` and `[::]:445` - and it must, because **Samba cannot bind an
IPv4 address on `tailscale0`**: the interface is a point-to-point TUN device without the
`BROADCAST` flag, which Samba's IPv4 interface selection skips. An explicit `interfaces` list
removes the Tailscale SMB path instead of securing it (verified with `<ip>/32`, the bare IP, and
the interface name).

Because this node's LAN interface also carries a globally routable IPv6 address, the wildcard
listener meant port 445 was bound on a world-routable address, with only the router's default
inbound-IPv6 block preventing reachability. The boundary is therefore enforced one layer down, by
the nftables table `inet smb_guard` (unit: `smb-guard.service`):

- inbound TCP/445 over IPv6 on the LAN interface -> dropped
- inbound TCP/445 over IPv4 -> accepted only from VM100 and the Proxmox host, the two nodes
  that actually mount; everything else on the LAN dropped
- Tailscale traffic arrives on `tailscale0` and is never evaluated

This is a kernel filter, applied *before* Samba sees the connection - unlike `hosts allow`, which
Samba applies after the TCP accept and which now serves as redundancy underneath.

**Never load this table via `nftables.service`:** the stock `/etc/nftables.conf` begins with
`flush ruleset` and the unit's `ExecStop` flushes everything - either would wipe Tailscale's own
`ts-input` / `ts-forward` chains.

Reasoning, measurements and reboot verification:
[SMB bind and LAN access](../decisions/smb-bind-and-lan-access.md).

## Failure Impact

VM102 represents a single storage failure domain.

If VM102 becomes unavailable:

- All dependent services lose access to their storage paths
- Containers may start but fail due to missing mounts
- Monitoring should detect mount and service degradation
- No data loss if disks are intact (recovery is procedure-based)

High availability is not implemented; recovery is procedure-based.

## Configuration Management

Managed via Ansible from LXC250.

- **Playbook:** `ansible/playbooks/apt-upgrade.yml` - rolling apt upgrade (`serial: 1`)
- **Role:** `ansible/roles/node_exporter/` - deploys node_exporter binary + systemd unit
- **Role:** `ansible/roles/ssh_hardening/` - `PasswordAuthentication no`, `PermitRootLogin no`
- **Role:** `ansible/roles/chrony/` - installs `chrony`, ensures started + enabled (time sync)
- **Note:** `PermitRootLogin` was explicitly set to `yes` before 2026-05-28 hardening - remediated by `ssh_hardening` role
- **Role:** `ansible/roles/snapraid_maintenance/` - deploys `snapraid-maintenance.sh` + sync/scrub timers
- **SSH access model:** primary admin path is the `ansible` user (key-based, NOPASSWD sudo). Break-glass fallback: the `storage` user's `authorized_keys` holds the two admin workstation keys (`admin-workstation`, `admin-laptop`), codified 2026-06-08 via the `breakglass` role (`ansible/roles/breakglass/`, `breakglass_user: storage`). `PasswordAuthentication no`, so key presence is the only access lever.
- **Break-glass keys are enforced, not merely added (2026-07-10).** The role sets `exclusive: true`, so `authorized_keys` is exactly `breakglass_pubkeys` and nothing else. This removed the stale `root@server` key that had survived every previous pass; the pre-existing file is preserved once at `authorized_keys.pre-ansible`. Adding a key now means adding it to `breakglass_pubkeys` - an ad-hoc `ssh-copy-id` is reverted on the next run, by design.
- **Time sync:** `chrony` installed (see [Time Synchronization](#time-synchronization)) via the `chrony` role.
- **NOT Ansible-managed - hand-deployed, would be lost on a rebuild (2026-07-14):** the Samba
  config (`/etc/samba/smb.conf`, mirrored sanitized in
  [snippets/storage](../../snippets/storage/smb.conf.storage-vm102.sanitized.conf)) and the SMB
  boundary (`/etc/nftables.d/smb-guard.nft` + `smb-guard.service`, sources in
  [snippets/storage/smb-guard.nft](../../snippets/storage/smb-guard.nft) and
  [snippets/systemd/smb-guard.service](../../snippets/systemd/smb-guard.service)). A backup of the
  pre-change `smb.conf` is kept on the node as `smb.conf.bak-2026-07-14`. Adopting these into a
  role is a follow-up, not done here.
