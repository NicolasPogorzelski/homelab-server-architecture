| 2026-07-14 | **vm102 (node touched, partially rolled back):** attempted step 1 of the SMB bind decision and **failed at the interesting part**. `hosts allow` lost its dead LAN entry (the admin desktop: no session, client log empty since 2026-06-17; it holds `tag:admin`, so ACL Rule 1 keeps its access over Tailscale) — that change **stands**. The explicit bind (`bind interfaces only = yes` + `interfaces = …`) was **reverted**: **Samba cannot bind an IPv4 address on `tailscale0`.** The interface is a point-to-point TUN device (`<POINTOPOINT,MULTICAST,NOARP,UP,LOWER_UP>` — no `BROADCAST`, which `ens18` carries) and Samba's IPv4 interface selection skips it. All three notations were tried against the live node with a restart and a socket check: `<tailscale-ip-vm102>/32` bound the Tailscale **IPv6** ULA but not the IPv4; the interface name `tailscale0` and the bare IP bound **nothing** on that interface. IPv6 succeeds where IPv4 fails because IPv6 has no broadcast concept. Client-side confirmation: with the bind active, `ncat -z <tailscale-ip-vm102> 445` was refused while the LAN address answered — i.e. an explicit bind *removes* the Tailscale SMB path rather than securing it. This retro-explains the `# Robust: listen on all available interfaces (avoid bind failures)` comment already sitting above a commented-out `interfaces` line in the live `smb.conf`: an earlier attempt hit the same wall and the reason was never written down. Rolled back from the timestamped backup; verified both paths reachable, six sessions intact, and the boot-order drop-in (`After=tailscaled.service`) removed again — with a wildcard bind it would delay startup for nothing. **Consequence:** the boundary moves one layer down to an nftables table on vm102 (`table inet smb_guard`: drop inbound TCP/445 over IPv6 on `ens18`, allow IPv4 only from vm100 and the Proxmox host), which is a kernel filter evaluated *before* Samba sees the connection — strictly stronger than `hosts allow`, which runs after the TCP accept. Planned, not yet applied; the load-bearing detail is that it must **not** go through `nftables.service`, whose stock `/etc/nftables.conf` starts with `flush ruleset` and whose `ExecStop` flushes everything — either would wipe Tailscale's own `ts-input`/`ts-forward` chains at boot. See [smb-bind-and-lan-access.md](../decisions/smb-bind-and-lan-access.md). |
| 2026-07-14 | Docs (repo-only, **no node touched**): recorded the SMB binding deviation on vm102 as a design decision ([smb-bind-and-lan-access.md](../decisions/smb-bind-and-lan-access.md)) and corrected `samba.md`, whose "Security Posture" section asserted **"No public exposure"** without evidence. Measured on the live node: `smbd` listens on `0.0.0.0:445` **and `[::]:445`** (`bind interfaces only = no`), and vm102's LAN interface holds a globally routable IPv6 address — so port 445 is bound on a world-routable address, and what prevents reachability is the router's default inbound-IPv6 block plus the absence of any IPv6 entry in `hosts allow`, not the service's binding. Access control is a post-accept application filter (`hosts allow`), not a bind — the same defect class as Apache on lxc210 and sshd on vm100. Established empirically (`smbstatus -b` + per-client `%m.log` files) who actually uses the three LAN entries: vm100 (`media-jf`, `media-abs`) and the Proxmox host (five mounts) are load-bearing; the third — an admin desktop — has **no session and an empty client log since 2026-06-17** and can be dropped. The long-standing objection to a Tailscale-only bind (throughput) was **measured and refuted**: same-subnet peers negotiate a direct WireGuard path over the LAN (`tailscale ping` → `via <lan-ip-vm102>:41641`, 2 ms), and 1500 MiB into a discarding sink gives **741 Mbit/s over Tailscale vs 809 Mbit/s over plain LAN — a ~8 % cost, not the uplink cap** the assumption predicted. Decision: step 1 (`bind interfaces only = yes` + three explicit IPv4 addresses, killing the `[::]:445` listener; drop the dead LAN entry) touches no mount and is safe; step 2 (moving the seven CIFS mounts to the Tailscale IP) is **deferred** until KE-15 is repaired, because a Tailscale-dependent mount can fail at boot before `tailscaled` connects — the KE-9/KE-12 class, and exactly the mechanism that hid KE-15 for a month. |

| 2026-07-10 | Repo tooling: `validate-repo.sh` gained **Check 16**, which runs `ansible-lint --nocolor` over `ansible/`. Checks 1–15 are structural and never look inside an Ansible file, which is why three commits passed the `PreToolUse` hook locally and turned CI red the same day. The check is a pre-commit net, not a second CI stage: it runs only when `ansible-lint` is on `PATH` **and** the diff touches `ansible/`, and prints `SKIP` otherwise. Under CI it always skips, because `actions/checkout` leaves a clean tree and `.github/workflows/ansible-lint.yml` already lints every push. Its weakness is stated rather than hidden: an uninstalled `ansible-lint` makes the check **silently inert**, so `pipx install 'ansible-lint==26.6.0'` (pinned to the workflow's version — a divergent local version would gate commits against a different rule set) is now a documented control-node prerequisite. Implementation notes: `ansible-lint` exits 2 on findings, which `set -e` would turn into a silent abort before the output is printed, so the call is captured with `&& rc=0 \|\| rc=$?`; the diff is read from `git diff --cached` with a `git diff HEAD` fallback for `git commit -a`, where the index is still empty when the hook fires. Verified against all three branches: `SKIP` with `PATH` stripped of `~/.local/bin` (exit 0), `PASS` on the clean tree (exit 0), and `FAIL` (exit 1, finding printed with file and line) after re-injecting the trailing blank line this same session had removed. The "no changes under `ansible/`" branch was not exercised and is noted as untested. |
