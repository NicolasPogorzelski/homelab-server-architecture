| 2026-07-10 | New known error KE-16 + fix (lxc210, live): `ServiceDown` fired for nextcloud. The certificate Apache was **serving** had expired an hour earlier (`notAfter=Jul 10 09:53:15`), while the certificate **on disk** in `/var/lib/tailscale/certs/` was valid to 8 October — `tailscaled` had renewed the file fifteen minutes before the old one lapsed. Renewal was never the problem: Apache reads its certificate at start-up and holds it in memory, and nothing told it to re-read. Diagnosed by reading the served certificate off the wire (`openssl s_client -servername`) rather than from the filesystem, after `curl` returned `ssl_verify_result=10` (`X509_V_ERR_CERT_HAS_EXPIRED`) while `curl -k` returned `302`. lxc210 is the only affected node: the other five certificate-holders (lxc200, lxc211, lxc220, lxc230, lxc240) terminate TLS through `tailscale serve`, which asks tailscaled per connection and renews transparently. Fixed immediately with `tailscale cert --min-validity 720h` + `systemctl reload apache2`; verified from lxc200 that the probe now returns `http=302 ssl_verify=0`. Durable fix: new `tailscale_cert` role — a daily `Persistent=true` timer running `tailscale-cert-refresh.sh`, which hashes the certificate, runs `tailscale cert --min-validity 720h` (a no-op above 30 days remaining) and reloads Apache **only** when the hash changed. New inventory group `tailscale_cert_ondisk` (added to `hosts.yml.example` too, since the live inventory is gitignored) so serve-backed nodes are never targeted. Detection had worked all along — `ServiceDown` fired within minutes and reached Discord; what was missing was the reload, and anything to stop the recurrence due on 8 October |
| 2026-07-10 | Fix (lxc260, live): PostgreSQL backups run again — first successful dump since 2026-06-14 (`pg_dumpall_20260710_103007.sql.gz`, 41 M), `pg_backup_last_success_timestamp` back to 77 s and `PostgreSQLBackupStale` resolved. Root cause: the role scheduled the dump as a **cron job at 03:00**, and the Proxmox host is powered down overnight by `homelab_schedule` and woken by RTC in the morning. lxc260's boot windows start between 05:32 and 14:11 — the container is never up at 03:00, cron has no catch-up, and the run is lost. The four dumps that did exist (9, 12, 13, 14 June) came from nights the host happened to stay up; the backup was never reliable, only lucky. `cron` itself was healthy (476 executions in 7 days). Replaced with a systemd timer + `Persistent=true`, which records the last run under `/var/lib/systemd/timers/` and fires an overdue job on the next boot; the legacy cron entry is removed by the role, since two schedules would both fire on a night the host stayed up. Second benefit: a failed timer unit now raises `SystemdUnitFailed`, whereas a cron failure was invisible. Also hardened `pg-backup.sh`: its pre-flight `[ ! -d "$BACKUP_DIR" ]` tested that the path exists, not that the CIFS share is mounted there — with the mount gone, `pg_dumpall` would have written ~42 M a night into the container rootfs, i.e. the thin pool on the boot SSD (the KE-7 class, and the third instance today of "existence checked where identity mattered"). It now requires `findmnt -no FSTYPE` to return `cifs`. **Note:** the script's `-mtime +7` retention deleted the four stale June dumps during this run, so exactly one backup exists until tomorrow's, and there is still no off-site copy |

| 2026-07-10 | Monitoring — alert on failed systemd units, closing the gap that let `calibre-import.service` fail ~20,000 times over a month (KE-15) behind a green dashboard. `node_exporter` gains `--collector.systemd`, which exports `node_systemd_unit_state`; without it a `failed` unit emits no metric at all and no rule can fire. Verified before rollout that the unprivileged `node_exporter` user may read unit state over the systemd D-Bus API. node_exporter's stock `--collector.systemd.unit-exclude` (`.+\.(automount\|device\|mount\|scope\|slice)`) is overridden to keep `.mount` units: **both** mount faults found today — lxc220's `/books-rw` and vm100's stale `media-mergerfs.mount` — are that unit type, so the default would have filtered out the very failure class the collector was added for. | 2026-07-10 | New role `systemd_hygiene` — masks or removes units that can never succeed on a given node, so the `SystemdUnitFailed` rule needs no permanent exception list and every alert means something. A rule that always fires is not read. Four units cleaned, each with its reason recorded in `host_vars`: lxc210 `run-rpc_pipefs.mount` (NFS plumbing from the `nfs-common` dependency; the node's storage is CIFS and `rpc-gssd` is inactive — verified no NFS mount exists before masking), lxc260 `nvmf-autoconnect.service` and `openipmi.service` (NVMe-oF and IPMI hardware that a container cannot reach), vm100 `media-mergerfs.mount` (legacy VirtioFS unit; the host no longer exports the `mergerfs` tag, `grep -rl /media/mergerfs` finds no consumer, and Jellyfin/Audiobookshelf read their libraries over autofs/CIFS from vm102 — already recorded as legacy in vm100.md). The role distinguishes two actions because they are not interchangeable: `mask` for package-provided units, `remove` for hand-written units already in `/etc/systemd/system`, where `systemctl mask` fails outright (`File ... already exists`) because the mask symlink and the unit file are the same path. It also clears the residual `failed` state, which masking leaves behind and which the exporter would keep reporting. Fleet-wide result: exactly one failed unit remains — `calibre-import.service` on lxc220, the real one. Idempotent over two consecutive full runs |

| 2026-07-10 | Fix (ansible, repo-wide regression introduced by `355b449` on 2026-07-08): `ansible-lint --fix` capitalised handler names to satisfy `name[casing]` but left the `notify:` references that point at them untouched. Ansible matches handler names by exact, case-sensitive string, so `notify: reload systemd` no longer resolved to the handler `Reload systemd`. Affected `calibre_importer` (2 tasks) and `postgresql_boot_order` (1 task) — the only two roles whose handler names contained a lowercase word. Verified empirically on a throwaway playbook rather than assumed: with the mismatch, `ansible-playbook` aborts with `The requested handler 'reload systemd' was not found` and `exit=1`; with the casing aligned, the handler runs. The failure is invisible until a notifying task actually reports `changed` — handler names are resolved at notify time, not at parse time — which is why both roles stayed green through idempotent runs and why `ansible-lint` (including `--syntax-check`) cannot detect it at any profile. Fixed by aligning the three `notify:` strings; the reverse (lowercasing the handlers) would re-trip `name[casing]` in CI |
| 2026-07-10 | New known error KE-15 — `calibre-import.service` on lxc220 has failed **every 2 minutes since 2026-06-08** (~20,000 times) and no ebook has been imported in that window. Chain: the host's rw CIFS mount `/mnt/smb/books-rw` is absent (not the transient boot-race the tech-debt note describes — a month-long steady state); the `mp2` bind therefore exposes the empty directory beneath it on `pve-root`; that directory is owned by host root, which in this **unprivileged** container appears as uid `65534`, so container root cannot write to it; `mkdir -p /books-rw/_import` returns `EACCES` and `set -euo pipefail` exits 1. **Both guards were structurally incapable of catching this**: `mountpoint -q /books-rw` in `calibre-import.sh:49` and in the role's `Verify the rw library mount is present` task returns success, because the `mp2` bind *is* a mountpoint regardless of whether the host-side CIFS mount succeeded — they tested a mount's existence where its identity was what mattered. Same structural error as `appdata_aux-disk` lacking `is_mountpoint 1`. Compounding it, the role's guard was a bare `command` without `check_mode: false`, so `--check` skipped it and reported the role healthy. Fixed repo-side: both guards now require `findmnt -no FSTYPE` to return `cifs` plus a present `metadata.db`; the script now exits **1** instead of the previous deliberate `exit 0` no-op (which is exactly why the outage was silent); the role's probe gained `check_mode: false` and the task order now deploys script + units *before* asserting the mount, so a broken host mount cannot block delivery of the script that handles broken host mounts. Verified: `--check --diff` against lxc220 now fails at the assert with `/books-rw has fstype 'ext4', expected 'cifs'`. **Host mount not restored** (deferred with the host block); the import path stays down until `/mnt/smb/books-rw` is mounted and `pct reboot 220` is run |
